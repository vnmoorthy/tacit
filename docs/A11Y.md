# Accessibility audit — Tacit

Report only; no components, styles, or design tokens were changed. Audited the running app at `http://localhost:5173` on **18 September 2026**, 14:34–14:36 PDT, using Chromium 151.0.7922.34 through Playwright.

## Scope and method

- Used a fresh, isolated browser context, `tacit.mode=local`, and the offline demo brain. Loaded the bundled samples into that context only. Blocked server API and external requests; no existing user captures, provider keys, microphone, or camera were used.
- Walked the actual tab order and activated controls with Enter on the landing page, empty/populated dashboard, new-capture form, settings, Maria's overview, knowledge base, Ask, handover, interview setup/text mode, and Constellation. Checked the dashboard's mobile tab order at 390 × 844; other checks used 1440 × 1000.
- Checked both the capture-delete and atom-edit overlays, DOM accessibility snapshots, computed focus styles, computed badge foreground/background colors, and every rendered HTML image on those routes. Inspected screenshots of the knowledge base, overlays, dashboard, and graph. Source references below identify the audited implementation.
- Severity: **High** blocks a core keyboard workflow or makes a modal unsafe to navigate; **Medium** materially impairs understanding or operation; **Low** causes avoidable friction.

## Findings

### A1 · High — Atom actions are inaccessible without hover

**Reproduce:** Open `/c/cap_maria/knowledge`, move the pointer away from the cards, and Tab through the filters. After “Story,” focus leaves the content and returns to navigation. None of the verify, edit, or delete actions can be reached. The live DOM contained **29 Edit buttons; zero were visible** without hover. Hovering a card exposed its actions.

**Cause/reference:** [AtomCard.tsx](../apps/web/src/components/AtomCard.tsx), lines 91–116, puts the actions inside `hidden ... group-hover:flex`; the article itself has no keyboard entry point.

**Suggested fix:** Keep the action buttons available in the tab order and reveal them on keyboard focus as well as hover. For example, use an opacity-based treatment with `group-focus-within` instead of `display:none`, or provide an always-visible, named Actions button. Adding only `group-focus-within:flex` to the existing hidden container is insufficient: focus must first be able to enter it. Verify, edit, and delete should work using Tab and Enter without moving the pointer. Relevant criterion: WCAG 2.1.1, Keyboard.

### A2 · High — Modals neither contain nor initialize focus

**Reproduce:** On the overview, focus More, press Enter, Tab to Delete capture, and press Enter. Focus lands on `body`; the next Tab reaches the **background coverage map**. Eleven background controls are traversed before the modal's Close button. Escape does not close the overlay. In the atom-edit overlay, Tab eventually leaves Save and returns to background navigation; Escape also does nothing. Neither overlay appears as a dialog in the accessibility snapshot (`role=dialog` count: zero).

**Reference:** Shared [Modal in ui.tsx](../apps/web/src/components/ui.tsx), lines 173–188; consumers in [CaptureOverview.tsx](../apps/web/src/pages/CaptureOverview.tsx) and [Knowledge.tsx](../apps/web/src/pages/Knowledge.tsx).

**Suggested fix:** Use a tested accessible dialog implementation or native modal `<dialog>`. Name it from the visible heading, move focus inside on opening, keep Tab/Shift+Tab inside, make background content inert, support Escape, and restore focus to the trigger on closing. Prefer initial focus on Cancel for destructive confirmation. Follow the [WAI-ARIA modal dialog pattern](https://www.w3.org/WAI/ARIA/apg/patterns/dialog-modal/). No deletion or edit was submitted during this check.

### A3 · Medium — Amber badge text fails minimum contrast

**Reproduce:** Open Maria's knowledge base and find a Gotcha badge, or the dashboard's “42 days left” amber badge. Gotcha uses `#8a4a12` text on opaque `#2a2013`: **2.33:1**, below the **4.5:1** requirement for its 11.5 px, weight-500 text. This is a text contrast failure even though the surrounding screen is dark. See the measured table below.

**Reference:** `TONES.amber` in [ui.tsx](../apps/web/src/components/ui.tsx), line 51; Gotcha mapping in [AtomCard.tsx](../apps/web/src/components/AtomCard.tsx), line 11; dashboard deadline and medium-confidence badge consumers in [Dashboard.tsx](../apps/web/src/pages/Dashboard.tsx) and [Ask.tsx](../apps/web/src/pages/Ask.tsx).

**Suggested fix:** Once a design-system change is authorized, use an approved lighter amber foreground that reaches 4.5:1 against the actual fill. Existing `--color-accent` (`#e8a33d`) is a candidate at approximately **7.41:1** on this fill. Recheck all amber consumers, including medium-confidence answers. This report does not alter the frozen palette.

### A4 · Medium — Domain filter is unnamed; several fields rely on placeholders

**Reproduce:** Tab to the domain selector in the knowledge base. Its accessibility snapshot is an unnamed `combobox`; “All domains” is its current option, not an associated label. Inspecting the search, question-queue, Ask, and interview-answer inputs shows no associated label or `aria-label`. Chromium falls back to their placeholder text as their accessible names, but the visible instruction disappears once someone types.

**References:** [Knowledge.tsx](../apps/web/src/pages/Knowledge.tsx), lines 104–113; [CaptureOverview.tsx](../apps/web/src/pages/CaptureOverview.tsx), line 229; [Ask.tsx](../apps/web/src/pages/Ask.tsx), line 224; [InterviewRoom.tsx](../apps/web/src/pages/InterviewRoom.tsx), line 410.

**Suggested fix:** Give the select a programmatic label such as “Filter by domain.” Give the text inputs persistent associated labels such as “Search knowledge,” “Question for the next interview,” “Ask Maria,” and “Your answer”; retain placeholders as examples. Reuse the existing `Field` pattern where suitable. Relevant criteria: WCAG 1.3.1, 3.3.2, and 4.1.2.

### A5 · Medium — Status feedback and toast dismissal lack accessibility semantics

**Reproduce:** From a fresh standalone dashboard, activate Load sample captures. The “Loaded 3 sample captures” toast appears, followed by a button with no accessible name. There is no `role=status`, `role=alert`, or `aria-live` region. The completed Ask answer and text-interview view likewise contained no live region. This confirms missing announcement markup; actual screen-reader speech was not tested.

**References:** [Toaster in ui.tsx](../apps/web/src/components/ui.tsx), lines 194–212; dynamic answer rendering in [Ask.tsx](../apps/web/src/pages/Ask.tsx), lines 164–210; transcript rendering in [InterviewRoom.tsx](../apps/web/src/pages/InterviewRoom.tsx).

**Suggested fix:** Name the icon button “Dismiss notification.” Announce ordinary operation results through a persistent polite status region and urgent errors appropriately. For interviews and answers, announce concise completed updates rather than continuously rereading the whole transcript. Relevant criteria: WCAG 4.1.2 and 4.1.3.

### A6 · Medium — Citation activation loses keyboard focus

**Reproduce:** On `/c/cap_maria/ask`, activate the suggested Friday ACH-rejection question. Focus citation `1` and press Enter. Its source card becomes highlighted, but `document.activeElement` changes to `body`. The buttons' accessible names are only “1,” “2,” and “3,” so their purpose is also unclear out of context.

**References:** Citation renderer in [Markdown.tsx](../apps/web/src/components/Markdown.tsx), lines 12–18; focus-state update and source cards in [Ask.tsx](../apps/web/src/pages/Ask.tsx), lines 190–200.

**Suggested fix:** Preserve the focused citation across the resulting render, or explicitly move focus to its named source heading. Give each chip a descriptive accessible name, such as “Show source 1: Friday rejections,” and associate it with the source. Retest sequential navigation after activation. The existing buttons are keyboard-activatable; this finding concerns lost focus and unclear purpose.

### A7 · Medium — Constellation has no accessible node/relationship representation

**Reproduce:** Open `/c/cap_maria/graph` and Tab through the page. The header controls are reachable; the graph's individual nodes are absent from both the tab sequence and the accessibility snapshot. The snapshot provides counts and a legend, but no traversable node or relationship list. All three canvas elements have `tabIndex=-1`, no accessible name, and no fallback text.

**Reference:** Graph container/canvas and legend in [Graph.tsx](../apps/web/src/pages/Graph.tsx), lines 857–967.

**Suggested fix:** Provide a named graph region with a keyboard-operable list/tree of nodes and their connections, with selection synchronized to the visual graph. Expose a clear route to the existing knowledge list as well. The labeled question field provides a keyboard text-entry path, and the app supports typed commands; that does not expose the graph's node and relationship inventory to assistive technology. Camera and voice operation were outside this audit.

### A8 · Low — Landing-page actions receive duplicate tab stops

**Reproduce:** Starting at the top of `/`, Tab through GitHub, Open the app, Try it now, and Watch the demo. Each action receives focus twice: first its link, then its nested button. This was recorded as consecutive `A` and `BUTTON` elements with the same text.

**Reference:** [Landing.tsx](../apps/web/src/pages/Landing.tsx), lines 51–60 and 78–86, plus the same pattern on later calls to action.

**Suggested fix:** Render navigation as one styled link rather than nesting a button inside it. Keep one accessible name and one tab stop per action.

## Focus visibility and successful keyboard checks

- The tab walks showed visible focus treatment on ordinary links, buttons, filters, switches, and form controls. The knowledge-base screenshot visibly showed an amber outline on the Procedure filter. Computed styles included 2 px focus outlines on links/filter buttons and focus treatment on shared controls. No general missing-focus-ring defect was found in these samples; A1, A2, and A6 describe the specific reachability/focus failures.
- The overview's textual coverage-domain buttons can be selected with Enter, providing a keyboard alternative to clicking the radial map. Their selection styling changes as expected.
- The More menu opens with Enter and its Delete capture item is reachable with Tab. The subsequent dialog is the failing portion described in A2.
- Sample capture cards, desktop navigation, mobile dashboard navigation, handover actions, and the text-interview setup controls are in the tab order. Type answers and Begin session worked with Enter in the isolated context.
- New-capture fields and settings selectors have associated labels. The Constellation question input has the explicit accessible name “Ask a question.”
- No JavaScript page errors occurred in the audited routes. This is operational evidence, not an accessibility-conformance result.

## Limitations and follow-up

This is a targeted browser audit, not WCAG certification. No VoiceOver/NVDA session, browser/OS matrix, high-contrast mode, 200–400% zoom/reflow audit, print-contrast audit, provider-backed voice session, camera/hand tracking, or phone dialog was tested. External font downloads and the remote demo video/vision assets were blocked; screenshots therefore use local fallback fonts, while the measured CSS colors remain applicable. Only the dashboard received a mobile-width keyboard pass. The local browser context was discarded after testing.

The checkout and running app were shared with concurrent work; references describe the implementation observed during this run. Recheck after integration. Prioritize A1 and A2, then amber contrast and control/feedback semantics. All proposed component/design fixes require separate authorization under [ASTRA_TASKS.md](ASTRA_TASKS.md); this task supplies findings only.

The combined task changes passed `pnpm typecheck`, all 39 tests, and `pnpm build`; full command output is in [ASTRA_VALIDATION.md](ASTRA_VALIDATION.md). Those checks do not resolve the accessibility findings above.
